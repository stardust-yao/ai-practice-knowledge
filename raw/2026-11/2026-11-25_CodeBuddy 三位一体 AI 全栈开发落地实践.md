作者：yorion，全栈开发工程师

接口挂了，业务还能不能继续？过去要对全部接口逐个注入故障、操作页面、观察结果，再把截图和结论整理到文档里。

快跑平台的强弱依赖分析功能把这些步骤串了起来：复用业务用例，逐接口注入故障，查看强弱依赖和判断依据，再导出报告用于复查。

*[图片]*

在已有平台上增加这项功能，既要确认“什么情况下能判断强弱依赖”，也要弄清已有执行器、变量和脚本怎样复用。代码写完之后，还要检查这些能力是否真正接起来，结果能否准确呈现在页面上。

本文记录了在 CodeBuddy 中处理这些问题的做法：怎样把模糊目标问清楚、留下方案取舍，再通过切片开发、测试和验收推进交付。

## 一、用 Grilling 把目标变成可判断的需求

一段话开始功能开发，先把需求讨论清楚

*[图片：Clipboard_Screenshot_1792757214.png]*

通过 `requirements-grilling` Skill，CodeBuddy 开展了 **7 轮集中需求澄清**：先确认使用者、业务痛点和实验依据，再讨论接口范围、业务校验、异常处理和结果证据。每轮确认的规则写入需求记录，保留来源和待决事项。

第四轮的接口识别讨论，能说明这些追问具体解决了什么。

要“逐接口分析”，首先得确定哪些请求算同一个分析目标。CodeBuddy 列出了查询参数、路径 ID、Method 和重复请求等样例，逐项给出建议：查询参数不同，是否忽略参数、合并分析？路径中的用户 ID 不同，是否识别成变量后合并？

*[图片：Clipboard_Screenshot_1792758738.png]*

逐项讨论后，最终选择了更明确的首版规则：**按 Method + 完整 URL 识别分析目标。** 查询参数、路径 ID 或 Method 不同，分别分析；完全相同的请求重复出现，则合为一个目标，但每次匹配都注入故障，并记录命中次数。

*[图片：Clipboard_Screenshot_1792758828.png]*

这次讨论把“逐接口分析”变成了可执行的规则：哪些请求分别分析、哪些合并、重复请求如何注入，后续都有据可查。代价也明确了：完整 URL 中的随机参数可能让下一次实验无法命中，需要如实记录为无法判定。**这里确认的是首版边界，而非一种通用的接口识别标准。**

> **Grilling 的作用：** 通过追问和具体样例，把双方各自默认的理解显露出来，形成共同决定。

这些问题怎样组织，也会影响讨论的效率。如果实验依据还没确定，就一路追问故障类型、匹配规则和失败处理，上游选择一变，前面的细节可能都要重谈。

因此，Skill 采用了 **BFS（广度优先）** 的思路：先找出前置条件已经确定的问题，放在同一批讨论；收到答案后，再展开依赖这些答案的下一批。

它在 Skill 中对应一条具体约定：**“找出前置条件已确定的决策前沿。”**

例如，确认采用故障实验后，可以讨论请求从哪里捕获、业务结果怎样校验；校验方式确定后，再深入异常如何处理。这样既减少零散问答，也避免过早钻进尚无依据的细节。

*[图片：Clipboard_Screenshot_1792756883.png]*

`requirements-grilling` Skill 把这套方法落实为四项约定：

- **按依赖分批问。** 每个问题记录前置决定，每轮只提出当前能回答的一小批，避免过早钻进细节。
- **按缺口选办法。** 事实查代码，需要取舍的问人，说不清的用样例或原型比较，缺少领域依据的明确记下。
- **把答案写回记录。** 保存决定、来源、状态和下游影响；已有答案不重复问，假设不能记为已确认。
- **明确何时继续。** 关键行为已对齐、剩余影响已明确，就推进不受阻塞的部分；规则冲突才继续澄清。

## 二、用 ADR 留住方案背后的判断

Grilling 形成了共同理解，后续开发还要知道这些决定为什么成立。

只留下“怎么做”，继续实现或修改时，就容易忽略原来的约束。

**ADR（架构决策记录）** 用来保存重要方案的选择理由，供后续实现和修改时查阅。

*[图片：image]*

需求澄清后让 CodeBuddy 通过 `domain-decisions` Skill 整理项目知识：术语和共同规则写入 `CONTEXT.md`，重要选择及其理由写入ADR。

*[图片：Clipboard_Screenshot_1792762896.png]*

后续接入平台能力时，就遇到了一个需要记录的选择：**已有执行器应该复用到哪一层？**

平台已经能执行点击、输入等页面操作，但依赖分析要求在请求发出前挂载故障拦截。CodeBuddy 检查调用链后发现，原执行器会自行创建页面并开始导航，外部无法提前挂载拦截；内部的页面动作函数却可以接收指定页面。

因此，最终选择是：**复用页面动作能力，由依赖分析管理浏览器上下文和实验编排。**

CodeBuddy 将调研依据、复用边界和执行约定写入ADR。

*[图片：Clipboard_Screenshot_1792761586.png]*

一份有用的 ADR 不需要很长，但应交代清楚：

构成

本例留下的内容

背景与约束

已有执行入口无法在导航前挂载故障拦截

方案与选择

复用页面动作能力，由新编排控制实验时机

理由与代价

保留已有实现，同时承担浏览器生命周期管理

状态与依据

记录接受与实施状态，关联代码调研位置和验证证据

`domain-decisions` Skill 约定了哪些判断值得留下：代码里能查到的实现细节不重复记录，重要取舍则保留理由、依据和变更关系。

## 三、"三位一体"：让全栈开发尽早得到真实反馈

方案明确后，怎样把任务交给 CodeBuddy？

如果只说“按方案实现”，前后端可能各自完成，却要等联调时才发现配置没有传下去、故障没有命中，或者结果没有展示出来。

先把已确认的要求写成可观察的行为，再安排每轮开发的范围。

例如，“支持精确匹配”还不足以直接开发, 它需要进一步明确：同路径的 GET 与 POST 分别分析，故障不能互相影响；相同请求重复三次，只形成一个分析目标，但三次请求都要注入，并记录命中次数。

`behavior-spec` Skill 将这些要求整理为行为规格和验收矩阵，写清前提、输入、预期行为和验证方式，并分配 AC 编号，供后续开发和验收引用。

*[图片：Clipboard_Screenshot_1792768019.png]*

第一条开发任务称为 S1，目标是先贯通一条最薄的完整路径：

**配置任务 → 保存 → 正常基线 → 故障实验 → 业务校验 → 存储结果 → 页面查看。**

这就是 **Tracer Bullet（曳光弹）** 的做法：先用一条最薄的真实路径检验各层能否协作，再沿它扩展。

开发这条路径时，还需要选定能够控制输入、观察结果的连接边界，也就是 **Seam**。

例如，页面同时请求接口 A 和 B，对 A 注入故障时，怎样证明 B 没有受到影响？让页面发出这两个请求：**目标请求 A 应被拦截，非目标请求 B 应正常到达站点。** 同时核对故障命中记录，就能检查注入范围是否正确。

*[图片：Clipboard_Screenshot_1792766248.png]*

*[图片：Clipboard_Screenshot_1792766276.png]*

有了明确的检查方式，就可以先把预期写成测试，再补实现。在开发分析执行器的时候采用了这样的推进方式： 先编写真实浏览器测试，运行时因实现入口还没完善而失败；随后实现初版捕获、故障注入和页面校验，再运行同一组测试，确认通过。

测试开发中，通常把失败阶段称为**“红灯”**，通过阶段称为**“绿灯”**。

*[图片：Clipboard_Screenshot_1792766384.png]*

红灯：测试已写好，执行器尚未实现，先确认测试能够发现缺失的能力。

*[图片：Clipboard_Screenshot_1792766407.png]*

绿灯：补齐执行器后，真实浏览器测试通过，继续推进存储和接口。

这体现了 **TDD（测试驱动开发）**：先用失败测试表达预期行为，再实现使其通过，必要时在测试保护下重构。

*[图片：03-trinity-fullstack-v2.png]*

这里的“三位一体”，是把最小完整路径、可验证的连接边界和测试先行结合起来：既尽早发现各层接不起来的问题，也能在关键行为上获得更短的反馈。

`vertical-slice-build` Skill 将它们落实为每轮开发约定：读取规格与依赖，选择当前具备条件的切片，在关键边界先测试、再实现，交付时附上对应验收结果与未完成项。

**规格明确完成条件，测试推动关键行为的实现**，这也是 SDD（规格驱动开发）与 TDD 在本次实践中的分工。

完整功能据此拆成十个切片。每个切片交付一组可验证的能力，所需的前后端改动一起推进：

切片

交付重点

完成时应能检查的行为
**S1 贯通主链路**
整套方案真实运行

配置、保存、实验、存储与页面贯通，关键平台配置参与执行
**S2 精确匹配**
只影响选定接口

域名、Method、参数隔离，重复请求全部命中
**S3 捕获窗口**
明确分析哪些请求

**S4 实验状态**
区分有效与无效实验

业务失败、脚本异常、未命中等分别判定，等级和统计一致
**S5 执行控制**
能停止，也能重跑

取消实际停止执行，时限生效，未执行项有原因，旧记录保留

检验真实场景的价值

这些编号不是固定执行顺序。S1 先提供真实路径，再按依赖扩展匹配、证据、状态、窗口和报告等能力；每轮将验收结果与剩余事项写回 `S-LEDGER.md`。

*[图片：Clipboard_Screenshot_1792766803.png]*

## 四、用证据定位问题，让修复有明确的终点

最小链路跑通后，还要检查用户能否看到完整的分析结果。

联调时就遇到了一个问题：接口的强弱依赖结论已经显示，但展开判断依据后，请求内容没有完整展示。问题出在数据采集、接口返回，还是页面渲染？

给 CodeBuddy 的要求是：**沿实际数据链路检查，每次固定同一次执行、同一个目标接口，核对具体内容。** 同时明确了需要检查和修正的证据字段及前后端命名。

检查位置

要回答的问题

数据库

目标接口的证据是否已保存？

API

保存的内容是否完整返回？

页面

展开对应目标后，内容是否实际显示？

*[图片]*

检查过程中发现了两处问题：前后端使用的字段名称不一致，接口返回路径也遗漏了 `evidence`。数据库里虽然已有证据，内容却没有完整传到页面。

其中，接口遗漏字段被测试明确捕获：返回结果已经包含依赖等级和判定原因，但 `API 应返回 evidence` 断言失败。

*[图片：Clipboard_Screenshot_1792831084.png]*

补回字段后，重新运行同一项检查，结果通过。

*[图片：Clipboard_Screenshot_1792832542.png]*

接口检查通过后，后续验收继续回到页面，展开目标接口，确认请求内容实际显示。页面核对结果、日志和截图一起保存在验收记录中。

*[图片：Clipboard_Screenshot_1792833022.png]*

`evidence-debugging` Skill 将这类排查要求固定下来：先运行能够捕获问题的检查，根据实际结果定位原因；修复后重跑原场景，保存验证记录。

*[图片：Clipboard_Screenshot_1792831470.png]*

有了这套约定，交给 CodeBuddy 的任务就不只是“把页面修好”，还包括找出原因、验证修改，并交出能复查的结果。开发者审查时，也能看到它改了哪里、检查了什么，还有哪些没有验证。

## 五、从用户操作到最终产物，验收完整交付

判断依据能够显示，说明这一处问题已经修复。

交付前，还需要按用户的使用顺序走完一遍：从导入已有用例开始，完成配置和分析，查看结果，再导出报告，检查这些操作能否顺利衔接。

因此，验收让 CodeBuddy 从界面完成连续操作：

**导入用例 → 改名保存 → 执行分析 → 查看结论与证据 → 立即重跑 → 下载报告。**

每一步都检查前一步留下的结果。导入后只修改名称，再核对参数、Cookie 和脚本是否保留；执行完成后，展开具体接口，检查结论与判断依据是否对应；重新运行后，确认新记录已经生成，旧记录仍可查看。

查看结果也不只是确认页面上出现了“强依赖”或“弱依赖”。

以健康卡展码页的结果为例，列表中能看到接口分类和断言结果，展开 `getQRCodeEncryptV2` 后，还能查看未通过的业务断言及正常、故障状态下的页面对比。

*[图片：image]*

*[图片]*

最后，实际点击下载 Markdown 和 PDF，并核对报告中的统计、接口结论和判断依据是否与对应执行一致。文件能够下载、内容是否齐全、排版是否可读，需要分别检查，不能只凭导出接口返回成功就结束验收。

## 六、留下工作状态，让下一轮开发接得上

验收完成后，还要沉淀记录，以便复利后续开发。

台账记录了切片进度：继续修改时，要知道沿用哪些规则、检查哪些条件，以及上次究竟验证到了哪里。

文档

保存什么

什么时候用

需求记录 `dependency-analysis.md`

用户确认的目标、范围、业务规则和待决问题

判断某项行为是否符合需求，区分已确认要求与建议
`CONTEXT.md`
术语、共同规则与稳定约束

开始任务时统一理解，避免同一个词在不同模块里含义不同
`ADR-*.md`
重要选择、理由、代价与状态

实现或调整方案时，查清为什么这样设计、哪些约束仍需遵守

行为规格 `dependency-analysis-spec.md`

输入、可观察的预期行为、验收编号与验证边界

编写测试和验收时，确定怎样才算完成

台账 `S-LEDGER.md`

各切片当前状态、对应验收项与证据入口

选择下一项任务，定位尚未完成的检查

验收记录 `docs/evidence/`

实际操作、失败与通过日志、截图、报告及限制

审查完成声明或继续排查时，核对实际发生了什么

*[图片：Clipboard_Screenshot_1792835673.png]*

**台账记录进度，链接具体依据。** 需求、方案、验收条件和测试结果各自更新在对应文档中，避免同一结论重复维护、彼此矛盾。

`context-handoff` Skill 将交接约定为每轮工作的一部分：结束时记录完成范围、验证结果、剩余问题和下一步；恢复时读取相关文档，并核对当前代码。

**ADR 留下“为什么这样设计”，交接记录明确“目前做到哪里，接下来怎么做”。**

以上做法整理成了 **工程实践技能（Full Engineering Skills）**
